## 一、更新提醒

### 用户能看到的变化

提醒保留三项：`ChatSync 有新版本 · <版本>`、`需要 DSH <目标版本声明的范围>`、一个更新按钮。没有声明宿主要求时如实显示「DSH 版本要求：未声明」。去掉更新说明摘要、读取失败提示和「完整更新内容」链接，关闭与同版本不重复提醒的行为保留。

宿主具备实际插件更新能力，且当前页面提供 `pluginNavigation.openBundle()` 时，按钮为「前往插件页更新」。它打开当前安装包的详情，由官方页面完成更新确认、安装和重启提示。不能仅因有「插件」页面就认为支持第三方插件更新，也不设置宿主最高版本或逐版白名单。

旧宿主或导航服务缺失时，按钮仍是「复制更新代码」。保留 Windows PowerShell、macOS 应用内终端命令和 Web 档案命令，精确指定目标版本、实际包名和 npm 官方源；复制失败时显示可选中的代码。两种入口均不能自动安装。

### 已核对的宿主依据

已安装的官方 DSH 0.2.2-rc.1 源码中，宿主服务提供 `pluginManager.updateBundle`；浏览器插件管理器提供可选的 `pluginNavigation.openBundle(packageName)`，选中 `plugins` 面板和已安装包详情，不改变当前会话。导航依赖当前页面的插件管理权限，不能放进 chatsync 的必需 `inject`。

可复核的上游位置：[插件页公开导航与交互说明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.1/packages/client/ui-plugin-manager/README.zh.md)、[浏览器插件页入口](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.1/packages/client/ui-plugin-manager/src/client/index.ts)。版本号仅记录核对环境，入口选择以实际能力为准。

### 检查与边界

- 自动检查覆盖有／无宿主更新能力、有／无导航、导航延后出现与卸载、两个包名、关闭后设置页再看、旧宿主各系统复制命令。
- 目标 npm 包名、版本与下载地址必须匹配；安装包未就绪、请求失败或无更新时不弹窗。缓存保留，但宿主能力变化不能被缓存固定。
- 从目标版本的 `engines.dsh` 读取要求，缺失时回退到 `peerDependencies['@deepseek-ai/dsh']`。不根据当前插件自己的要求猜测新版要求。
- 可点击 HTML 只验证文案与示意交互；真实宿主服务、官方页面导航、实际安装分别记录，不能相互替代。

本轮实际边界：10 个相关测试文件共 177 个用例最终通过，包含更新专项 18 项；旧 API 断言修正后单独重跑该文件，不是一次完整 `npm test`。生成一致性、ESLint、格式、类型及安装包内容检查通过。依赖追踪选出的全仓检查因范围过大中止，另有沙箱环境失败记录，均不计为通过。

安装版 DSH 0.2.2-rc.1 / Electron 44.7.0 在独立空数据目录加载本轮源码副本，真实 npm 查询及原生更新能力返回通过；另以合成 0.21.3 元数据检查新版本响应，不调用安装。浏览器停留在首次引导后连续超时，尚未观察到插件详情跳转终态。HTML 已通过脚本与命令静态检查，浏览器因本地文件协议策略未能打开，尚需维护者检查显示与点击。未更新日常安装；完整发布回归、macOS 实机与物理双机均不在本轮已通过项中。

## 二、自管 SSH 裸仓库

### 需求与现有阻塞

issue #25 的具体需求是：管理员先在自己的服务器执行 `git init --bare` 建好空仓库，插件经 SSH 同步。无需在 0.21.3 中安装或管理服务器软件，也无需调用 GitHub/Gitee/GitLab API 建仓。

现有 Git 传输基本可以复用，缺口在连接模型和私有性检查：

1. `lib/remote.js` 要求至少两段路径，不能接受 `user@host:repo.git` 或 scp 风格的绝对路径；还会为 SSH 地址强制生成同主机 HTTPS 网页与探测地址。
2. `lib/engine/remote-repo.js` 的非 GitHub 验证需要同路径 HTTPS 明确要求登录。只开 SSH、HTTPS 路径不同或没有 Web 服务的机器会被拒绝。连接保存与每轮同步都会执行该检查。
3. 界面将 `remoteWeb` 同时当作地址可用的依据。自管仓库不一定有网页，必须拆开地址有效性、可连接状态与可选网页链接。

### 首版范围建议

新增显式「自管 SSH 服务器」连接类型，现有「代码托管站」流程保持现有验证方式；不得在 HTTPS 检测失败时自动切到自管类型。

| 项目 | 0.21.3 建议范围 |
| --- | --- |
| 仓库 | 服务器上预先创建、已有 SSH 账号权限的裸 Git 仓库；空仓库首推与已有同步仓库接入 |
| 地址 | `user@server.example:repo.git`、`user@server.example:/srv/git/repo.git`、`ssh://user@server.example:2222/srv/git/repo.git` |
| 登录 | 使用本机 OpenSSH、密钥、ssh-agent 和 `known_hosts`；插件不收集私钥或口令 |
| 数据 | 主数据、项目分支、备份分支和设备回执沿用既有传输与安全规则 |
| 不在首版 | 自动建远端仓库、部署 SSH 服务、任意远程 shell、公开仓库、本地／file／git 明文协议、关闭主机密钥校验 |

建议先要求明确主机名或 IP 和用户；SSH 配置别名、IPv6 与复杂 ProxyJump 的完整支持另列后续范围。若首版纳入其中任何一项，需要补充目标绑定与真实连接验收，不可仅凭 Git 理论支持就声明可用。实现时不得悄悄忽略用户已有 `sshCommand` 或其他本机 SSH 配置。

### 开始实现前需要确定的信任方案

**纯 Git over SSH 没有通用的“仓库是否私有”接口。** 认证成功只证明当前账号可以读取；匿名连接失败、没有 HTTPS、Unix 权限或仓库里的声明文件，均不能证明没有其他公开导出入口。

建议采用单独的「管理员确认访问范围」模式：管理员明确确认仓库只供授权账号访问、没有公开导出；插件验证本机可以认证读取，并将这一依据如实显示为「管理员已确认访问范围」，不能称为「已自动验证私有」。这会扩展当前 [维护约定](../AGENTS.md) 中的私有性确认机制，**本规划仅提出建议，尚未取得采用该模式的决定；执行智能体不得自行移除现有上传检查**。

如果仍要求程序自动取得服务端私有性证明，需要另行设计并信任服务端策略接口，明确证明范围；单纯裸仓库无法满足这一要求。该路线的服务端工作量应重新评估，不能先删掉检查再补。

若管理员确认模式获得接受，实施时满足以下约束：

- 确认只在本机保存于既有排除范围，绑定连接类型、完整 SSH 目标、策略版本及本机解析后的目标身份；不随设置同步到另一台电脑。
- 更换用户、主机、端口、仓库路径或影响连接身份的 SSH 配置时，原确认失效。主机密钥变化由 OpenSSH 拒绝；不能自动写入信任或改用其他目标。
- 不只比较原始地址：需核对实际的 SSH 目标解析及 Git 的 URL 重写。无法确认真实目标与已确认目标一致时停止，不上传。
- 每轮上传、项目同步、历史重建／清理等写远端路径走同一信任判断；无确认、确认过期或检查失败时停止受影响操作。
- 托管站的公开仓库拒绝规则保持有效；不得把网络失败或 SSH 成功当作自动获取声明的途径。

### 连接与保存流程

1. 选择「自管 SSH 服务器」，填写仓库地址；本机先在终端完成密钥、主机指纹和访问权限配置。
2. 校验地址并解析本机实际连接目标；拒绝密码、令牌、控制字符、选项与路径注入。使用参数数组调用 Git，不拼接 shell。
3. 按已决定的信任方案取得目标确认，执行无交互的只读连通检查。检查不能向远端写探针数据、改配置或建仓。
4. 检查完成后重新核对 `expectedRemote`、宿主覆盖和同步状态，取得既有进程锁后保存。本机配置和确认材料需保持一致，写入失败不能留下半个新连接。
5. 首次正常同步才上传；空裸仓库创建所选同步分支。只读账号的写权限失败应有明确提示，不误报为保存时已验证可写。
6. 切换失败保留原连接，不向新旧任一目标继续本轮传输。正常切换不搬迁全部历史，也不删除旧仓库；迁移沿用现有文档的边界。

## 三、分阶段执行与验收

| 阶段 | 交付物 | 退出条件 |
| --- | --- | --- |
| A：当前更新入口 | 代码、聚焦回归、可点击示意、宿主能力核对记录 | 主智能体复核；维护者能检查三项文案、关闭与两个入口 |
| B：连接方案定案 | 信任方案、首版地址范围和拟交付文案 | 维护者明确选择信任机制；未选择时可继续独立测试设计，不实现绕过 |
| C：模型与上传检查 | 地址解析、本机确认、统一验证、保存并发保护 | 失败路径及旧托管站回归通过，不接触个人远端 |
| D：界面与真实 SSH | 连接 UI、帮助、专用 SSH 裸仓库测试、隔离宿主检查 | 有成功与失败的终态记录；目视入口可用 |
| E：候选准备 | 文档一致性、完整回归、候选安装包及隔离试装 | 按 [发布安全清单](release-safety-checklist.md) 复核，随后另行确认发布授权 |

必须覆盖的验收矩阵：

- 地址：三种首版形式、单段仓库、端口、非法路径／协议／凭据；未纳入的形式明确拒绝。
- 信任：无确认、过期、目标改变、SSH 配置或 URL 重写改变、HTTPS 不存在、托管站公开仓库；不能自动放行。
- SSH：正确密钥、错误账号／密钥、首次未知指纹、指纹变化、带口令密钥但无 agent、超时和只读账号；插件不弹出无人处理的密码输入。
- Git：空裸仓库首推、两个隔离数据目录往返、主数据／项目分支、已有仓库、路径错误、非裸目录、只读远端。Git 能读取不能单独证明目标是裸仓库；需明确测试与服务器准备要求。
- 切换／并发：验证时另一保存或同步开始、宿主配置覆盖、写配置／确认失败；主仓库和项目影子仓库不能写错远端。
- 数据保护：会话严格追加、官方格式校验、覆盖前备份、删除必经确认、凭据排除与脱敏、失败不报整轮成功。
- 平台：Windows 11／Electron 为主要实际环境；Web、macOS 的自动测试与真实宿主检查分别记录。macOS 无实机时保持未验证，不借命令生成测试宣称实机通过。

自动测试默认临时目录、合成数据、本地裸仓库、`autoRepo: false`。真实 SSH 测试使用专用测试服务器和仓库。新增服务器路径建议做物理双机往返，由维护者决定是否执行及是否作为本次发布条件；一台机器的双副本不算物理双机。
