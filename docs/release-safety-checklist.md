# 发版前数据安全检查（分级门禁）

适用于每次候选定版、打发布标签、npm 发布和 GitHub Release，包括重试发布。门禁按版本级别要求不同的必过项；所有项目默认「未验证」。必过项失败、缺证据、跳过、取消、中断、待用户核对或与候选版本不一致，均禁止定版、打发布标签和发布。不得通过删检查、降低断言、复制旧结论或手填成功绕过。

本地验证能证明的是：固定源码、候选包、指定环境与场景下，检查的安全条件成立。不能据此承诺所有环境永远零风险。未知格式、未知状态及超出支持范围的输入，必须验证其安全停止行为。没有所需设备或环境，就保留阻断状态，不能把模拟改名为实机验收。

## 一、按版本级别的必过项

`scripts/check-release-safety.mjs` 按 `package.json` 的版本号判断级别：修订号大于 0（如 0.21.1）为补丁版，其余（如 0.22.0、1.0.0）为次版本。

| 清单 ID | 补丁版 | 次版本 | 必须达到的结果 |
| --- | --- | --- | --- |
| `full-regression` | 必过 | 必过 | 冻结源码执行完整回归，独立 Node 与 Windows 桌面端内置运行时（Electron）分别记录终态、退出码、总数、通过/失败/取消/跳过数。退出码为 0、无失败/取消、无跳过；超时不算通过 |
| `candidate-install` | 必过 | 必过 | 使用 SHA-256 已记录的实际候选 tgz，装入隔离宿主，完成实际加载、公开接口读写、冷启动；核对载入文件哈希及版本/构建、包文件清单与源码 ZIP 对应源码；安装命令成功不算通过 |
| `physical-two-device-github` | — | 必过（维护者确认即可） | 两台物理设备经专用私有 GitHub 仓库完成 A 上传 → B 取回 → B 新增 → A 取回，并重启读回；由维护者实际操作后确认，记录两端环境、候选包哈希和结果。同机双副本、本地 Git、隔离宿主均不能替代 |

下文五类风险的场景和恢复演练是参考检查：按本版改动涉及的风险选做，做了就逐项记录在清单的 `advisory` 中；不要求全部完成，但任何一项记为 `failed` 都会阻断发布，必须先处理。

## 二、参考检查：每类风险的四层证据

以下五类风险各有四层检查，共 20 项，另有恢复演练 `restore-drill`。每一层都要记录覆盖了下文哪些场景及对应结果；可以共用报告，但报告必须逐条列出场景、预期和实际结果，不能只填「已通过」。

| 清单后缀 | 必须提供的证据 | 不足以代替它的材料 |
| --- | --- | --- |
| `source-review` | 从入口追到扫描、快照、合并、写入、提交、回执和恢复；标出源码位置、分支条件、失败路径、原件保存位置，以及每条安全条件由谁保证 | 只搜索关键词、只看函数名、单纯无语法错误 |
| `automated` | 有独立预期数据的行为断言；逐项核对事件内容、序号、数量、身份、归属、附件哈希和原件字节；保留命令、退出码、终态统计 | 仅验证返回值成功、两边都变空、拿被测结果当预期 |
| `fault-injection` | 在隔离目录和测试远端注入故障，记录触发位置、种子、时间线、前后哈希、停止/恢复/重试结果 | 只做正常往返，或只把接口替身设成报错 |
| `native-runtime` | 实际 DSH 宿主加载候选源码/包，通过公开接口写入、读回、重启后再读回；记录真实宿主/Node/Electron、插件版本、构建及载入文件哈希。涉及提示/确认须有真实 Desktop 窗口操作记录 | 用 Desktop 内置 Node 跑测试、安装命令退出成功、浏览器接口夹具 |

恢复可核对完整会话与附件；源文件会因合法追加改变时，检查故障前已确认的事件没有丢失，不能只比较整个文件哈希。对要求保留的原件/冲突分支，逐字节或 SHA-256 校验。

## 三、五类风险及参考场景

### 1. 静默丢失、覆盖或误删（`data-loss`）

- [ ] **L1 首次使用及空目录：** 新设备、未挂载目录、读失败、配置损坏、扫描不完整不等于用户删除；不能向其他端传播批量删除或用空结果覆盖完整会话。
- [ ] **L2 双方各有新增：** 同一会话严格追加时保留全部完整事件；离线分叉、同名工作区、身份碰撞保留双方，不能按时间戳或文件较大直接丢弃一边。
- [ ] **L3 用户操作意图：** 明确删除、归档、取消归档、移除工作区与正常未分组分别处理；既不能误删，也不能让已删除内容无故复活。
- [ ] **L4 并发写入：** 生成中、附加进程持续写日志、附件仍在写入、两实例同时同步；快照必须完整且对应同一代，不覆盖活动宿主尚未落盘的内容。
- [ ] **L5 幂等与真实完成：** 重复同步、重复导入、旧请求晚到、推送被拒后重试，不丢事件、不重复创建；尚未应用、只有部分工作区成功、等待核对时不能报告整轮同步成功。

通过条件：以同步前独立保存的事件清单和双方原件为基准，所有应保留的内容可定位、可读回，身份/项目归属/附件正确；无法安全选择时停止并保留双方。

源码与现有验证入口（须检查当版内容，不代表已覆盖全部场景）：`lib/sync.js`、`lib/merge.js`、`lib/session-transfer.js`、`lib/host-sync.js`、`lib/session-removals.js`；`tests/two-device.test.mjs`、`tests/session-merge.test.mjs`、`tests/session-transfer.test.mjs`、`tests/session-removals.test.mjs`、`tests/host-sync.test.mjs`、`scripts/check-dsh-desktop.mjs`。

### 2. 损坏被当成正确结果扩散（`corruption-spread`）

- [ ] **C1 残缺输入：** 半行 JSONL、半个压缩帧、序号缺口、重复/乱序事件、日志与索引不一致、未知格式和超出容量限制；完整性未知时不能发布完成回执。
- [ ] **C2 写入中断：** 在快照、合并、临时文件写入、替换、提交、推送前后分别终止进程；恢复后只能保留可验证的旧状态或完整新状态，不能留下混合状态覆盖好副本。
- [ ] **C3 存储故障：** 磁盘满、权限不足、文件被占用、备份写失败、目录不可达；必须保留原件并给出失败，不能继续危险写入或报告成功。
- [ ] **C4 远端/网络故障：** 拉取失败、推送拒绝、认证失效、断网、响应丢失、远端历史变化；固定已检查的提交，重试不得误传未核对数据。
- [ ] **C5 修复保护：** 自动/手动修复不得根据残缺副本补造正文；安排修复、执行中断、修复完成待核对和确认放行各状态均重启验证，待核对期间禁止继续传播。

通过条件：任何注入点失败后，完整副本不受污染；错误可见，重试可接续，校验无法确定时安全停止；修复和回执状态与实际磁盘及宿主读回一致。

入口：`lib/session-safety.js`、`lib/session-repair.js`、`lib/data-health.js`、`lib/data-repair-worker.mjs`、`lib/session-transfer.js`；`tests/issue4-stress.test.mjs`、`tests/session-safety.test.mjs`、`tests/compatibility-repair.test.mjs`、`tests/data-health.test.mjs`、`scripts/check-issue4-safe.mjs`、`scripts/check-data-repair-native.mjs`。打包行必须按逻辑事件验证，不能用物理行数代替事件数；官方恢复器的版本和实际执行结果必须留证。

### 3. 隐私超出用户授权范围（`privacy`）

- [ ] **P1 隐藏位置：** 用合成凭据覆盖当前文件、旧会话工具输出、附件、冲突副本和传输副本，确认上传前检查实际候选内容；不能只扫当前凭据文件。
- [ ] **P2 范围边界：** 导出、预览、导入均遵守关闭项和忽略规则，含已跟踪文件、无 Git 项目、嵌套目录及符号链接/目录联接；不能越界读写或把用户保留本机的内容重新带入。
- [ ] **P3 远端身份：** 私有仓库、正确账号与目标、最小必要权限；公开/不可确认仓库、更换目标失败、配置损坏时停止，不能回退到另一个远端继续上传。
- [ ] **P4 脱敏与历史：** 脱敏生成独立身份副本、原件字节不变、实际宿主读回成功；合成凭据上传被拦截，扫描失败也不能默认放行。删当前文件不算清除远端历史。
- [ ] **P5 证据本身：** 错误提示、诊断、测试日志、截图、npm 包和源码 ZIP 不含真实凭据、个人会话或本机隐私备份；公共证据只用合成/脱敏材料，凭据命中证据不能保存凭据值。

通过条件：用精确的合成标记检查待上传树、传输副本和远端所有本轮可达提交，未授权内容为零；原件保留在不会再次同步的位置。不能把敏感扫描器视为能识别所有秘密的保证。

入口：`lib/privacy.js`、`lib/privacy-copy.js`、`lib/scope.js`、`lib/connection.js`；`tests/privacy.test.mjs`、`tests/privacy-copy.test.mjs`、`tests/scope.test.mjs`、`tests/private-remote.test.mjs`、`tests/connection.test.mjs`。

### 4. 更新与环境差异造成批量事故（`upgrade-environments`）

- [ ] **U1 历史兼容：** 每个声明支持的旧会话格式、压缩代际、旧配置、旧远端历史、未提交内容；升级后往返及冷启动读回，旧原件不变。未支持格式应安全停止。
- [ ] **U2 混合版本：** 新旧客户端轮流同步、并发写入、降级/回滚；旧版不能误解新增删除语义或新格式后静默覆盖，无法兼容时明确阻止。
- [ ] **U3 Windows 真实条件：** 中文/空格/长路径、大小写碰撞、同名项目、锁文件、目录联接、OneDrive 目录中的并发替换与冲突副本；模拟干扰及真实 OneDrive 测试目录观察分别记录，不将普通目录结果算作 OneDrive 通过。
- [ ] **U4 宿主与生命周期：** 声明支持的 Web/Desktop 与实际运行时组合；启动时编辑、正常退出、托盘、强退、重启、休眠/唤醒、断网重连；后台重试不打断编辑、不丢草稿/附件，也不能因强退未上传而误报成功。
- [ ] **U5 发出的就是测过的：** 冻结源码、版本、构建标识、npm 包及源码 ZIP 清单；排除机器名冲突副本、个人数据、输出目录，包内运行文件与冻结源码一致。更换代码、默认值、依赖、宿主或候选包后，相关证据失效并重跑；本轮指纹不允许套用旧版报告。

通过条件：支持矩阵每个组合有实测结果和明确边界；未通过组合必须阻止不安全操作并调整支持声明，不能用「可能兼容」定版。

入口：`tests/session-upgrade.test.mjs`、`tests/config-migration.test.mjs`、`tests/scheduler.test.mjs`、`tests/process-control.test.mjs`、`scripts/check-session-upgrade-native.mjs`、`scripts/check-lifecycle-desktop.mjs`、`scripts/check-runtime-regression.mjs`、`scripts/pack-local.mjs`。先审查脚本的输入、输出及退出逻辑再执行，尤其历史脚本是否复用固定输出目录；不得覆盖旧证据。

### 5. 出事以后无法找回（`recovery`）

- [ ] **R1 先有可靠备份：** 替换、合并、修复、恢复之前保存原件，确认备份完整且可读；备份失败必须阻断后续危险写入。备份位置不进入同步范围，不被后续同步或清理一起覆盖。
- [ ] **R2 真正恢复：** 故意破坏隔离数据，仅靠保存的备份在新目录恢复，通过真实宿主冷启动核对正文、事件、附件、身份和归属；不能只证明备份文件存在。
- [ ] **R3 恢复不再受污染：** 恢复后仍面对坏远端、旧客户端和未完成任务时，不能立即再次覆盖恢复结果；用户核对并明确放行后才继续传播，重启也保留保护状态。
- [ ] **R4 中断与撤销：** 恢复/修复各阶段取消、强退、再次运行和撤销，不丢新的有效内容，不重复导入；没有可靠来源时明确指出无法恢复的部分。
- [ ] **R5 普通用户走得通：** 实际 Desktop 窗口能找到失败原因、受影响内容、查看/恢复入口、待核对项及确认动作；由操作记录证明能完成一次恢复。不得用「同步成功」掩盖仍需人工处理。

通过条件：从已知故障恢复到独立预期数据，故障前内容可验证，故障后新增也受保护；记录恢复耗时、恢复到哪个时间点、未恢复部分及原因，不承诺无法保证的零丢失时间。

入口：`lib/recovery.js`、`lib/session-recovery.js`、`lib/recovery-guide.js`；`tests/recovery.test.mjs`、`tests/session-recovery.test.mjs`、`tests/recovery-guide.test.mjs`、`scripts/check-data-repair-native.mjs`。

## 四、恢复演练（参考）

`restore-drill`：按 R1–R5 完成一次端到端灾难恢复，保存独立期望清单、故障前/后及恢复后比对、用户确认与继续同步结果。涉及恢复、修复或备份路径的版本应当执行。

## 五、实际执行与证据格式

1. **冻结候选范围。** 提交唯一维护源中的全部候选代码、检查脚本、测试和文档；记录支持矩阵。未登记源码不能漏出冻结范围，机器名冲突副本须显式处理。不要在本轮顺带发布或改个人同步配置。
2. **生成清单。** 在仓库运行 `node scripts/check-release-safety.mjs --init`。它只创建 `release-evidence/<版本>/manifest.json`：`checks` 是本版级别的必过项，`advisory` 是参考检查，初始均为 `pending`，已有文件不会覆盖。运行 `node scripts/check-release-safety.mjs --fingerprint` 获取已冻结源码指纹，填入 `sourceSha256`。它不包含 `release-evidence/`，避免报告与指纹循环依赖；其他受版本控制文件全部纳入。
3. **打包及验收。** 归档候选 tgz 至 `outputs/`，记录 SHA-256 到 `packageSha256`；必过项及记录的参考检查必须针对同一源码/包。CI 需要重现相同字节的 tgz；使用 Git 原始内容的干净检出（关闭自动换行转换），一致的 npm/Node 与打包设置。哈希不同就重新核对、验收，不能直接改哈希放行。不得用打包准备目录或旧标签证明日常宿主已运行新包。
4. **保存材料。** 原始日志、截图、安装包、部署备份保存本机 `outputs/` 的本次新目录。仅将合成/脱敏且足以复核的报告、终态记录、比对结果和必要截图复制到 `release-evidence/<版本>/`，纳入版本控制；逐个填写 SHA-256。公开前检查敏感内容，不提交原始个人数据。每份报告记录本轮源码指纹、候选包哈希、测试命令及参数、环境、开始/结束时间、逐场景结果和限制；旧证据可以作背景链接，不能直接勾本轮通过。
5. **逐项复核。** 每个 `checks` 项只有满足所有对应安全条件才改为 `passed`；做过的参考检查同样填写；填写 `completedAt`（含时区的 ISO 时间）、`environment`、`procedure`（命令或可重复操作步骤）、`observed`（具体结果）、`reviewer`（实际复核人）和 `artifacts`（至少一份 `{ "path": "release-evidence/<版本>/报告文件", "sha256": "64位小写哈希" }`）。失败保留 `failed`；未完成保留 `pending`，不得填「不适用」绕过。证据可以共享，但结论必须逐项可查。
6. **门禁与定版。** 提交脱敏证据后保持工作区干净，运行 `node scripts/check-release-safety.mjs --package <候选tgz绝对路径>`。只有退出码 0 才能认定本轮证据门禁通过；再根据用户授权执行定版、打标签、推送和发布。任何安全相关疑点未解决，即使机器检查通过，也不得定版。发布授权与安全通过是两个独立条件。
7. **发布时再次检查。** 发布工作流重新生成候选包、核对清单及证据、执行完整测试，再发布被核对的同一 tgz。发布后检查 npm 实际包及 GitHub 日志/完整源码 ZIP；保留该次发布提交和制品哈希。工作流修改只有推送后生效。

门禁脚本校验项目完整性、通过状态、必要记录、源码指纹、候选包哈希，以及已提交证据文件存在且哈希一致；不能自行判断报告是否真实、是否充分覆盖源码语义。维护者必须阅读证据并完成上述复核，不能把 JSON 通过当成所有风险已消失。
