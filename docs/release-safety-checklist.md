# 发布安全检查

适用于正式定版、发布标签及对外发布。维护分工与授权边界见 [AGENTS.md](../AGENTS.md)，日常检查见 [贡献指南](../CONTRIBUTING.md)。本清单不要求每次执行全部风险参考场景。

## 默认必过项与双机选择

| 清单 ID | 发布要求 | 实际检查与证据 |
| --- | --- | --- |
| `full-regression` | 所有版本默认必过 | 冻结候选下的完整回归，独立 Node 与 Windows/Electron 分别记录命令、环境、终态、退出码及通过/失败/取消/跳过数；退出码 0，无失败、取消或跳过 |
| `candidate-install` | 所有版本默认必过 | 实际候选 tgz 装入隔离宿主，核对包、载入文件与版本/构建，完成加载、公开接口测试数据读写及重启读回；安装命令成功不能代替检查结果 |
| `physical-two-device-github` | 默认参考项，按维护者当次决定 | 真实两台物理设备经专用私有测试远端完成 A 上传 → B 取回 → B 新增 → A 取回和重启读回，记录两端环境、候选包及结果 |

智能体自动执行完整回归和候选包试装，只使用隔离测试数据，不使用真实会话；主智能体复核技术结果与证据并报告，维护者无需观看执行过程。视觉、文案和实际点击逻辑由维护者目视确认，具体分工见维护约定。

涉及同步、删除、恢复或新增服务器连接方式时，智能体说明双机验收必要性并准备数据和步骤，维护者决定是否进行、是否要求发布前完成。界面和文案等改动不强制双机；未做如实记录，由维护者结合检查结果判断发布影响。

模板将双机项放入 `advisory`，未做不阻断。要求本次发布前完成时，将其从 `advisory` 移至 `checks`，不能两处重复；此时未完成按必过项阻断。旧 schema 2 清单中已列入 `checks` 的双机项目仍是本次必过项。物理双机不能由同机双副本、本地 Git、隔离宿主或单台实网结果替代。

脚本保留 `tier` 作为版本描述：修订号大于 0 为 `patch`，其余为 `minor`；两类默认必过项相同。现有双机 ID 为兼容既有清单保留，不改变其真实两台设备与专用远端的验收含义。

## 失败、未验证与当次决定

- 必过项缺失、失败、跳过、中断、待确认或缺少终态，不能记为通过。实际失败必须先处理，参考项记录为 `failed` 也阻断。
- 可选双机未做保持未验证；CLI 会显示未验证或未记录，不能据此声称已通过。参考双机标为 `passed` 时同样核对完整记录与证据哈希。
- 现有 `ownerDecision` 只允许对 `candidate-install` 或已列为必过的双机项，接受其 `not-verified` 状态；不能豁免完整回归、实际失败、缺失项目、损坏证据或候选绑定不一致。
- 此决定不将未验证改为通过，仍须完整记录及证据，并在更新日志和验证记录公开说明限制。决定只绑定本次候选，不成为未来发布的通行证。

`ownerDecision` 必须包含 `mode: "release-with-unverified-scenarios"`、本次 `version`、`build`、`sourceSha256`、`packageSha256`，以及非空的 `instruction`、`reason`、`requestedBy`、有效且不晚于当前时间的 `requestedAt`、不重复的 `acceptedChecks`。不得为方便放行而由智能体虚构维护者决定。

## 执行顺序

1. **明确发布范围。** 确定渠道、版本、改动影响与双机选择。只授权 GitHub 不自动授权 npm；当前自动流程会发布两者，详见贡献指南。
2. **准备并冻结候选。** 在维护源中完成代码、生成文件、测试和文档，提交候选源码并打包实际待发布的 tgz；记录版本、构建、源码及包范围。隔离检查不得修改个人同步配置或对个人原件注入故障。
3. **生成清单。** 运行 `node scripts/check-release-safety.mjs --init` 创建本版 `manifest.json`；已有文件不会覆盖，应先核对其与当前候选的关系。运行 `node scripts/check-release-safety.mjs --fingerprint` 获取已冻结源码指纹，记录实际候选包哈希。
4. **执行检查。** 针对上述冻结源码和候选包完成默认必过项及当次要求的项目；按改动选择风险参考。保存原始命令、环境、起止时间、终态与限制，不覆盖旧记录。
5. **绑定制品与材料。** 填入实际候选 tgz 的 SHA-256；把合成或脱敏、足以复核的记录纳入 `release-evidence/<版本>/`，逐份记录 SHA-256。原始材料按本机约定归档，不提交真实凭据或个人内容。
6. **复核并运行门禁。** 主智能体核对实际结果、范围与证据；提交脱敏材料，保持工作区干净，运行 `node scripts/check-release-safety.mjs --package <候选tgz路径>`。退出码 0 只表示机器门禁通过。
7. **按授权发布并核对。** 维护者完成所需目视确认、双机决定与发布授权后，按实际渠道执行；核对最终 tgz、源码 ZIP、校验值、日志与版本。

## 清单字段与证据要求

文件位置为 `release-evidence/<版本>/manifest.json`，当前 `schemaVersion` 为 `2`。

| 字段 | 内容 |
| --- | --- |
| `version`、`build`、`tier` | 与 `package.json` 的版本、构建及脚本推导级别一致 |
| `sourceSha256` | `sourceFingerprint` 生成的源码指纹 |
| `packageSha256` | 实际待发布候选 tgz 的 SHA-256 |
| `checks` | 两项基本必过项，加上维护者当次要求必过的双机项 |
| `advisory` | 选择性风险参考与默认可选双机项；不得出现未知或重复 ID |
| `ownerDecision` | 仅在维护者明确作出当次有限验证发布决定时填写 |

每项记录包含 `id`、`status`、`completedAt`、`environment`、`procedure`、`observed`、`reviewer`、`artifacts`。模板初始为 `pending`；满足条件才记 `passed`，失败保留 `failed`。`completedAt` 使用有效且不晚于当前时间的 ISO 时间；操作、结果、环境与复核人不能只填空白。

必过的通过项、接受的未验证项以及参考双机通过项，均须至少一份 `artifacts`：`{ "path": "release-evidence/<版本>/报告文件", "sha256": "64位小写哈希" }`。文件必须非空、可读取、已纳入版本控制，位于本版本证据目录内；不能使用越界路径、符号链接或不匹配的哈希。可共用报告，但结论逐项可查。

门禁还核对干净工作区、版本、构建、项目完整性、源码指纹及实际候选包哈希。短包名制品另由发布打包脚本核对 `shortPackageSha256`；不能把主包哈希当作短包哈希。

## 候选变化与发布重试

源码指纹使用 Git 索引中的全部受版本控制内容，**仅排除 `release-evidence/`**；文档、脚本等也会影响指纹。证据文件自身另行校验哈希，避免循环绑定。

源码或包变化后，重新核对清单、候选与证据适用范围，重跑受影响的检查。纯文档或证据整理不机械重跑无关行为检查，但须为当前候选写可复核的适用性说明并引用原始记录；保留原始测试的真实范围和结果，不能直接替换哈希假称重新测过。无法证明适用时重跑。

当前机器门禁仍严格比较当前源码指纹、实际包哈希和已提交报告哈希，不会自动按文件影响判断证据可复用。候选绑定发生变化后，须完成上述复核、记录与必要检查，再更新清单绑定。

相同候选的发布重试不机械重复完整产品测试，前提是候选与证据仍一致。当前发布工作流执行门禁与更新测试、包内容检查并复核候选绑定证据，不会再运行产品全套；若重打包字节变化，先查清差异并重新处理候选，不能直接改哈希放行。

## 按改动选择风险参考

| 改动风险 | 建议核对 |
| --- | --- |
| 同步与删除 | 首次空目录、双方新增、显式删除意图、分叉原件保留、重复同步及部分失败回执 |
| 损坏与并发 | 残缺日志、序号缺口、并发写入、磁盘或进程中断、恢复与重试后内容完整 |
| 隐私与远端 | 私有可确认目标、凭据文件与本机字段排除、疑似密钥提醒、连接失败安全停止、证据脱敏 |
| 宿主与升级 | 实际宿主接口、旧格式与配置、冷启动、不同运行时、候选包加载文件一致性 |
| 恢复 | 覆盖前原件保存、独立预期数据、真实宿主读回、未恢复部分与恢复后防污染 |

既有参考 ID 包括五类风险（`data-loss`、`corruption-spread`、`privacy`、`upgrade-environments`、`recovery`）分别组合四种方法（`source-review`、`automated`、`fault-injection`、`native-runtime`），以及 `restore-drill`。它们是选做工具，不是每版额外必须全跑的 21 项。具体入口与条件见 [脚本说明](scripts.md)。

机器校验不能证明报告真实或覆盖全部安全语义；主智能体应报告实际验证范围、未验证部分和重要限制。检查通过与对外发布授权是两个条件，不能互相替代。
